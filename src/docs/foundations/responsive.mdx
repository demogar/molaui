# Responsive

<DecisionsBehind foundation="Foundations/Responsive" />

Mola UI is built for screens people work at all day, but every screen has to hold on a phone
too. Three rules shape how: a component responds to the space it is given, not to the window;
a screen reflows at 320px; and density never excuses breaking either rule.

## Breakpoints

Six viewport breakpoints, all in `rem`. Tailwind sorts media queries by value and cannot sort
mixed units, so when `nav` was in pixels it came out before `sm` and won where it should have
lost ([ADR 0007](?path=/docs/decisions-0007-a-closed-bridge--overview)). A breakpoint applies from
its width up, so `sm:flex-row` means "a row from 40rem". `nav` is Mola's own: it is where the
application shell's sidebar becomes a sheet.

<BreakpointTable />

The table is read from `theme.css`, and the components column is checked against the source, so
it changes when a component starts or stops using a breakpoint. Most of the library responds at
`sm` alone, and nothing uses `xl` or `2xl`.

## Respond to the container, not the window

A component rarely knows how wide its slot is. A stat group can sit across a 1440px dashboard or
in a 360px side panel on the same monitor. A viewport breakpoint would lay it out for the monitor
in both places. So components that sit in panels of unknown width use **container queries**: the
element is marked `@container` and its children respond with `@md:`, `@3xl:` and the other steps
below.

- **Stat groups** go from one column to two at `@md` and to their full count at `@2xl` to `@4xl`.
- **A message** puts its author beside the text from `@lg`, and above it below that.
- **A file diff** shows the split view from `@3xl` and a single column below.
- **Dialog and drawer footers** lay their actions out in a row from `@sm`, and stack them full
  width below that.
- **Pattern screens** name their containers (`@container/settings`, `@container/agents`), so a
  nested container cannot answer for them.

<ContainerTable />

The same steps set widths with `max-w-*`: `max-w-page` for an application page, `max-w-wide` for a
dashboard, `max-w-reading` for a column of prose. The reading measure is in `ch`, so it follows the
type size rather than the window.

**Use a viewport breakpoint for the page, and a container query for a part.** The page gutter,
the shell and the page's own grid answer to the window. Anything that could be dropped into a
panel answers to its container.

## Reflow at 320px

A screen must work at 320 CSS pixels wide, which is what WCAG 1.4.10 measures (a 1280px window
zoomed to 400%). Nothing scrolls sideways except a region that is meant to: a table, a code block,
a row of tabs or chips. That region carries the `scroll-edge` utility with `useScrollEdge()` as its
ref, and draws a stitched edge while there is more past it
([ADR 0009](?path=/docs/decisions-0009-scroll-edge-cue--overview)). Table, Tabs and CodeBlock
already do. A solid keyline says the panel ends. A stitched one says the cloth goes on.

The browser audit narrows every story to 320 by 568 and fails it when:

- the page scrolls sideways;
- text is cut by a container that cannot scroll to show it (a deliberate ellipsis is allowed);
- text is painted over other text or over a control;
- a number does not fit its field;
- a region scrolls sideways without the scroll-edge cue.

It also checks every page at 390px, the phone most people hold, because a layout can break at one
width and not the other.

## At every density

Density is the reader's choice as much as the product's: someone who needs larger text and taller
targets chooses `spacious`. So a screen must still reflow at 320px in spacious. WCAG 1.4.10
makes no exception for a setting the user picked, and the pages that need room most are the ones
used at the largest density.

Today the audit measures the composed screens (the patterns, the agent console, the application
shell and the form example) at spacious density, at 1024, 768 and 320px. Some single components
still overflow a 320px phone at spacious density. That is a [known gap](?path=/docs/mola-ui-known-gaps--overview),
and fixing them is tracked in [issue 130](https://github.com/demogar/molaui/issues/130).

## Type does not follow the window

The type scale changes with [density](?path=/docs/foundations-density--overview), not with the
viewport, so a label is the same size on a phone and on a monitor. The one exception is `Display`,
the hero heading of an empty state or an introduction page, which is set fluid between 40 and 76px.
A narrow screen narrows the reading column, never the text. See
[Typography](?path=/docs/foundations-typography--overview).

## Checklist

1. Build the part with a container query if it could ever sit in a panel.
2. Look at it at 320px wide, in the comfortable and the spacious density.
3. Give every region that is meant to scroll sideways `scroll-edge` and `useScrollEdge()`.
4. Let long labels wrap. Never set a fixed width that holds text.
5. Keep targets at least 24px, even in compact.
