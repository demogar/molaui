# Color

Every swatch on this page is painted from the live CSS variable, split down the middle into the
light and dark theme, and labelled with the value and ratio **computed from `tokens.css`** by the
resolver the contract test uses. If a label disagreed with its paint, the build would already be
red.

## Washes

A mola has no tints, so washes are reserved for a whole region that belongs to a layer without
becoming it: a callout, a selected row, a running step. Mixed thin enough that **every step of the
ink ramp stays legal on every wash**.

## Roles: danger, accent, selection

A layer says what a thing is made of; a role says what it means. Components use the role, so the
meaning is in the code and an app can re-dye a role without repainting a layer. **On a product
screen rojo is used only through the danger role**: a red rótulo band, list marker or agent name
beside a red FAILED mark made the failure one red thing among several
([ADR 0008](?path=/docs/decisions-0008-the-rojo-register--overview)). The
editorial accent (rojo links and list markers in `Prose`) is the one exception, and a test holds
the components to it.

## Scopes: what each colour is for

Tailwind generates every colour utility for every token, so `text-cloth-pale` compiles as readily
as `bg-cloth-pale`. Only one of them was measured. Each colour token is therefore scoped to the jobs
it does, from five: a **surface** carries content, **text** colours words, an **edge** is a line, a
**mark** is a small graphic that is not a region, and an **overlay** sits over content the system
cannot know. A token can have several: rojo fills a panel, reads as text on cloth, keys a swatch
and is a cut band. Gold has no text scope, because it fails on light cloth; the status tones have
none either, because words in a status take `--ink-danger` and its kin, which `on-layer` collapses
on a filled panel.

<ScopeTable />

A test reads every component and pattern and fails on a colour utility outside its token's scope,
and fails if a promised pairing puts a token in a role its scope does not allow. The agent docs list
each token's valid utilities, and `tokens/mola.tokens.json` carries the same scopes as Figma
variable scopes (`com.figma.scopes`) with the CSS variable as code syntax, so a Figma kit built from
it offers a surface only as a fill.

## Two themes, one declaration

```css
--cloth: light-dark(#edeee8, #16181c);
```

Each token is written once with both values, and `color-scheme` picks one. That buys three things
a duplicated `[data-theme=dark]` block does not: the OS preference is honoured with no script, any
subtree can flip theme on its own, and a token cannot exist in one theme and be forgotten in the
other.

The colour tokens are declared on `:root` and again on every `[data-theme]` element. A browser
that reads `light-dark()` natively doesn't need the second one. A production build does: Lightning
CSS rewrites `light-dark()` for older browsers into custom properties, and those resolve where the
token is declared, not where it is used. With the tokens on `:root` alone, a dark panel inside a
light page would paint light. The browser audit checks that every `data-theme` subtree paints its
own ground, and the light and dark halves of the swatches on this page are two such subtrees.
