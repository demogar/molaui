# Content and voice

<DecisionsBehind foundation="Foundations/Content and voice" />

An internal tool is read under pressure: a run has failed, an agent wants permission, a table has
a hundred rows. The words have to say what happened and what each button will do, in as few
words as that takes. This page gathers the rules the components already follow, so a screen
built from them sounds like one product.

## Three voices

Every piece of text on a screen comes from one of three speakers, and the typeface says which.
A reader can tell from the letterforms alone whether the product, a person or the machine is
talking, which matters most in an agent transcript where all three sit together.

## The rules

These are the design rules that are about words. They are the same rules a review applies and the
agent manifest publishes, read from one source.

<ContentRules />

In practice:

- **Name the action and its object.** “Delete run”, “Save name”, “Retry from step 3”. A button
  that names its consequence can be chosen without reading the dialog above it.
- **Never “OK”, “Yes”, “Submit” or “Are you sure?”** A confirm button repeats the verb of the
  question: the title asks “Delete this run?” and the button says “Delete run”.
- **Say what happened, then what to do.** An error is a fact and a way out: “report.pdf is not an
  accepted type. Use PDF or CSV.” Not “Invalid file”, and not an apology.
- **Status is a word as well as a colour.** Queued, Running, Needs approval, Failed, Cancelled.
  The glyph and colour help a glance; the word is what a screen reader and a greyscale screenshot
  keep.
- **Figures are tabular and carry their unit.** “1,204 tok”. Numbers compared down a column line
  up, and none of them is set in monospace.
